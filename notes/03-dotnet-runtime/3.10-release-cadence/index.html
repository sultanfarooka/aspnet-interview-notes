    3.10 — Release Cadence: LTS vs STS¶

    ← Roadmap · Section: 3. .NET Runtime and Platform Prev: 3.9 .NET Standard · Next: 4.1 What ASP.NET Core is

    Markers: ⭐ · Confidence: 🔴 · Last reviewed: —

    TL;DR¶

    .NET ships a new major version every November, and each one is supported for a fixed period depending on whether it is LTS or STS.

    • Even numbers are LTS — Long-Term Support, 3 years. .NET 8, 10, 12.
    • Odd numbers are STS — Standard-Term Support, 18 months. .NET 7, 9, 11.
    • Both are equally stable. STS is not a preview or a beta — it is a full release with a shorter support window.

    Definitions¶

    Term What it is What it means
    LTS a support track Long-Term Support. 3 years of patches. Even-numbered releases.
    STS a support track Standard-Term Support. 18 months of patches. Odd-numbered releases.
    Cadence a release rhythm .NET ships one major version every November, without exception.
    End of support (EOL) a date After it, no more security patches. Running past it means known unpatched vulnerabilities.
    Patch release a version like 10.0.3 Bug and security fixes only. No new features. Safe to take immediately.
    Servicing the patch process Monthly patch releases, usually on the second Tuesday.
    global.json a file in your repo Pins which SDK version builds this repository. See 3.8.
    Roll-forward a runtime behaviour An app built for 10.0.0 will run on 10.0.5 automatically. Patch versions are compatible.
    Go-live a support status A preview Microsoft will support in production. Rare, and still a preview.

    The concept¶

    Why there are two tracks¶

    Different organisations want opposite things from a release schedule.

    Some want stability. A bank or a hospital system does not want to upgrade its runtime every year. Every upgrade means regression testing, change approval and risk.

    Some want the newest features. A startup shipping daily would rather have the latest performance improvements immediately.

    Microsoft serves both with alternating tracks. Every November there is a release; every other one is supported for three years instead of eighteen months.

    A picture: a bus route with two kinds of stop. Buses come at the same regular interval, but some are express services that stay in service much longer. You catch whichever suits how often you want to change buses.

    ⚠️ STS is not a beta¶

    This is the most common misunderstanding, and it is worth being precise about in an interview.

    .NET 9 is not "less finished" than .NET 8. It is a complete, production-ready, fully supported release. It receives exactly the same quality of patches. The only difference is that the support window is 18 months rather than 3 years.

    In fact STS releases often contain features that appear in the next LTS after being proven — they are where new work lands first.

    How it works¶

    The simple version — the schedule¶

    Version Released Track Support ends
    .NET 6 Nov 2021 LTS Nov 2024
    .NET 7 Nov 2022 STS May 2024
    .NET 8 Nov 2023 LTS Nov 2026
    .NET 9 Nov 2024 STS May 2026
    .NET 10 Nov 2025 LTS Nov 2028

    Notice something in that table: .NET 7 went out of support before .NET 6 did, even though it came out a year later. An 18-month window that starts later can still finish earlier. That catches people out when planning.

    Always check the current dates against Microsoft's support policy page before an interview. This table is a memory aid, and the dates move as new versions ship.

    How it actually works — choosing a track¶

    Choose LTS when:

    • Upgrading is expensive — heavy regression testing, formal change control
    • You are in a regulated industry
    • The application is stable and rarely touched
    • You have many services and cannot upgrade them all frequently

    Choose STS when:

    • You deploy often anyway, so upgrading is routine
    • You want a specific new feature now
    • You have good automated test coverage, making upgrades cheap

    The honest default for most teams is LTS. Not because STS is worse, but because a three-year window means you upgrade on your own schedule rather than to a deadline. Most organisations underestimate how much friction a forced upgrade creates.

    But there is a trap in the middle. Staying on LTS and skipping every STS means jumping two major versions at a time — .NET 8 straight to .NET 10. That is a bigger change with more breaking changes at once than two smaller steps. If your team upgrades easily, taking every release is often less painful overall.

    Patch releases and roll-forward¶

    Every month, usually the second Tuesday, Microsoft ships patch releases: 10.0.1, 10.0.2 and so on. These contain only bug and security fixes, never new features.

    Take them promptly. They are where security vulnerabilities get fixed, and they are designed to be safe.

    Roll-forward makes this easy. An app built against 10.0.0 automatically runs on 10.0.5 if that is what is installed — patch versions are binary compatible. You do not have to rebuild to pick up a security patch on the runtime.

    You can control the behaviour in runtimeconfig.json:

    {
  "runtimeOptions": {
    "rollForward": "latestPatch"
  }
}
    Setting Behaviour
    latestPatch Default. Use the newest patch of the same major.minor.
    minor Roll forward to a newer minor if the exact one is missing.
    major Roll forward across major versions. Risky.
    disable Exact version only. Fails if it is missing.

    The deeper detail — running past end of support¶

    Once a version reaches end of support, no more security patches are issued. Ever.

    That is not a minor operational detail. It means:

    • Any vulnerability found afterwards stays unpatched in your deployment, permanently.
    • Public CVEs tell attackers exactly what to try.
    • Compliance frameworks — PCI DSS, SOC 2, ISO 27001 — generally treat unsupported runtimes as an audit finding.
    • Container base images stop being updated, so vulnerability scanners flag every build.

    Running on an unsupported .NET version is a security problem, not a technical debt item. Being able to frame it that way is genuinely useful, because it is the argument that actually gets upgrade work prioritised. "We should upgrade for the performance" loses to feature work. "We are running an unpatched runtime with published CVEs" does not.

    Pinning the SDK¶

    The runtime and the SDK are versioned separately. A global.json pins which SDK builds your repository:

    {
  "sdk": {
    "version": "10.0.100",
    "rollForward": "latestFeature"
  }
}

    Without it, whoever has the newest SDK installed builds with it, and subtle differences appear between developer machines and CI. See 3.8.

    Code¶

    Checking what you are on and what is installed:

    dotnet --list-runtimes      # every runtime present, side by side
dotnet --list-sdks          # every SDK present
dotnet --info               # everything, including the OS

    Upgrading a project is usually one line:

    <!-- Before -->
<TargetFramework>net8.0</TargetFramework>

<!-- After -->
<TargetFramework>net10.0</TargetFramework>

    Then rebuild and run the tests. In practice most upgrades are close to that simple — .NET has a strong compatibility record — but check the breaking changes list first, and expect some package updates to be needed alongside.

    A sensible upgrade order:

    1. Read the breaking changes page for the target version.
    2. Change the TFM in one project and build.
    3. Update packages that complain.
    4. Run the full test suite.
    5. Deploy to a non-production environment and watch memory and latency for a day.

    That last step matters because the differences that bite are usually runtime behaviour changes — a GC default, a thread-pool heuristic — rather than compile errors. .NET 9's DATAS change (3.4) is a good example: nothing fails to compile, but memory behaviour in containers changes.

    Interview questions¶

    Q: What is the difference between LTS and STS?

    Both are full production releases shipped every November. LTS — Long-Term Support — gets three years of patches and lands on even-numbered versions like .NET 8 and .NET 10. STS — Standard-Term Support — gets eighteen months and lands on odd numbers. The common misunderstanding is that STS is somehow a preview or lower quality. It is not: same stability, same patch quality, only a shorter support window. STS releases are often where new features land first before appearing in the next LTS.

    Q: Which would you choose for a new project?

    Usually LTS, because a three-year window means you upgrade on your own schedule rather than against a deadline, and most organisations underestimate the friction of a forced upgrade. I would choose STS if the team deploys frequently anyway and has good automated test coverage, so upgrading is routine, or if there is a specific feature worth having now. There is a trap in between though — staying on LTS and skipping every STS means jumping two major versions at once, which bundles more breaking changes into a single step than taking them one at a time.

    Q: What happens when a version reaches end of support?

    No further security patches are issued, so any vulnerability discovered afterwards stays unpatched in your deployment permanently — and because CVEs are published, attackers know exactly what to try. Container base images also stop being updated, so scanners flag every build. Most compliance frameworks treat an unsupported runtime as an audit finding. I would frame it as a security issue rather than technical debt, because that is the argument that actually gets the upgrade prioritised against feature work.

    Q: How do patch releases and roll-forward work?

    Patch releases ship roughly monthly and contain only bug and security fixes, never new features, so they are safe to take promptly. Roll-forward means an application built against 10.0.0 will automatically run on 10.0.5 if that is what is installed, because patch versions are binary compatible — you do not need to rebuild to pick up a runtime security fix. The default policy is latestPatch, and you can change it in runtimeconfig.json if you need stricter or looser behaviour.

    Traps ⚠️¶

    • "STS is a beta." It is a full production release. Only the support window differs.
    • A newer version can go out of support first. .NET 7 ended before .NET 6 did.
    • Skipping every STS makes upgrades harder, because you jump two majors at once.
    • Running past end of support is a security problem, not just outdated tooling.
    • The SDK and runtime are versioned separately. A newer SDK can build for an older runtime.
    • Without a global.json, different machines build with different SDKs.
    • Upgrade problems are usually runtime behaviour, not compile errors. Watch memory and latency in a test environment before shipping.
    • Always verify the current dates. The schedule moves every November.
