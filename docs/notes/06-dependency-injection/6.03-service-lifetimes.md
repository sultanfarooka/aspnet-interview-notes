# 6.3 — Service Lifetimes: Transient, Scoped, Singleton

## TL;DR

- **Transient** = a new instance every time it's injected. **Scoped** = one per HTTP request. **Singleton** = one for the application's lifetime.
- The consumer's lifetime wins: a transient injected into a singleton effectively becomes a singleton.
- `DbContext` is scoped. Registering it as a singleton is the classic wrong answer — it isn't thread-safe and its change tracker grows forever.

---

## The concept

Every service you register with the DI container has to answer one question: *when
someone asks for this, do I hand back a fresh object or one I made earlier?*

That's the entire idea. The three lifetimes are three answers to it, and picking the
wrong one produces bugs that don't show up until you have concurrent traffic — which is
exactly why interviewers ask about it. It's a question where the wrong answer is
invisible in development.

---

## How it works

The container tracks instances per **scope**. A scope is an `IServiceScope` — a container
that lives for a bounded period and disposes everything it created when it ends.

In ASP.NET Core, the framework creates a scope at the start of each HTTP request and
disposes it when the response completes. That's why "scoped" and "per request" are used
interchangeably in web apps — but they aren't the same thing, and that distinction is the
follow-up question. A `BackgroundService` has no ambient scope, so scoped services must
be resolved from a scope you create yourself.

| Lifetime | Instance per | Disposed when | Thread safety needed |
|---|---|---|---|
| Transient | every resolution | the owning scope ends | no (usually) |
| Scoped | scope (= HTTP request) | the request ends | no |
| Singleton | application | app shuts down | **yes** |

Singletons are shared across concurrent requests. That means any mutable state inside one
must be thread-safe — and this is where most singleton bugs actually come from, not from
the registration itself.

## Code

```csharp
builder.Services.AddTransient<IEmailFormatter, EmailFormatter>();
builder.Services.AddScoped<IOrderRepository, OrderRepository>();
builder.Services.AddSingleton<IPricingCache, PricingCache>();

// DbContext is registered scoped by default — this is AddScoped underneath.
builder.Services.AddDbContext<AppDbContext>(o =>
    o.UseSqlServer(builder.Configuration.GetConnectionString("Default")));
```

Proving the behaviour to yourself is worth doing once:

```csharp
public class LifetimeDemo(
    ITransientService a, ITransientService b,
    IScopedService c,    IScopedService d)
{
    // a.Id != b.Id  — two separate instances
    // c.Id == d.Id  — same instance within this request
    //                 but a different Id on the next request
}
```

Resolving a scoped service where no scope exists — a `BackgroundService`, a hosted
service, or startup code:

```csharp
public class OrderCleanupService(IServiceScopeFactory scopeFactory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            using var scope = scopeFactory.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

            await db.Orders
                .Where(o => o.ExpiresAt < DateTimeOffset.UtcNow)
                .ExecuteDeleteAsync(stoppingToken);

            await Task.Delay(TimeSpan.FromMinutes(5), stoppingToken);
        }
    }
}
```

The scope must be created **inside** the loop, not outside it. A scope held for the life
of the service is a singleton `DbContext` wearing a disguise.

## Interview questions

**Q: Explain the three service lifetimes in ASP.NET Core.**

Transient gives you a new instance every time it's resolved, so it's for cheap stateless
things. Scoped gives you one instance per scope, and in a web app the framework creates a
scope per HTTP request — so it's one per request, which is what you want for a
`DbContext` or anything representing a unit of work. Singleton gives you one instance for
the whole application, which is right for caches and configuration, but it means the
instance is shared across concurrent requests so any mutable state has to be thread-safe.

**Q: What happens if you inject a scoped service into a singleton?**

The singleton captures it on first construction and holds it forever, so a
request-scoped object becomes application-scoped. With a `DbContext` that's genuinely
bad: it isn't thread-safe, so concurrent requests corrupt its internal state, and its
change tracker accumulates every entity it has ever seen, which is a memory leak. The
container catches this at startup in development because scope validation is on by
default there — but it's off in production, which is the part people miss. If a singleton
genuinely needs a scoped service, inject `IServiceScopeFactory` and create a scope per
operation.

**Q: Is a transient service ever effectively a singleton?**

Yes, and this is the part that surprises people. Lifetime is a property of the object
graph, not the registration. If a singleton takes a transient in its constructor, that
transient is resolved once and lives as long as the singleton. "Transient" only describes
how often the container *creates* one, not how long the result survives.

**Q: Why is `DbContext` scoped rather than transient?**

Because it's a unit of work. You want every repository and service handling a single
request to share one context so change tracking and `SaveChanges` cover the whole
operation atomically. Transient would give each consumer its own context and its own
separate transaction, which defeats the point.

## Traps ⚠️

- **"Scoped means per class or per controller."** It means per *scope*. In a web request
  that's per request; outside one there is no ambient scope at all.
- **"The container will stop me registering this wrong."** Scope validation is enabled in
  the Development environment only. The same code can start cleanly in production and
  fail under load.
- **"Singleton is faster, so prefer it."** Only if the object is genuinely shareable and
  thread-safe. Otherwise you've traded an allocation for a race condition.
- **"`AddSingleton(new Thing())` and `AddSingleton<Thing>()` are equivalent."** They
  aren't for disposal: the container disposes what it creates, so if you hand it an
  instance you built, you own its lifetime.
