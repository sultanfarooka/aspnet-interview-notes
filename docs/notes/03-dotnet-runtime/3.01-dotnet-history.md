## TL;DR

There have been **three generations of .NET**: Framework (2002, Windows only), Core (2016,
the cross-platform rewrite), and .NET 5+ (2020, where the names merged back into one).

- **.NET Framework 4.8 is the final version, forever.** Security fixes only. No new features.
- Today there is just **one .NET**. ".NET 8" or ".NET 10" always means the modern one.
- **.NET 4.8 and .NET 8 are unrelated products.** The similar numbers are an accident of history.

## Definitions

| Term | What it is | What it means |
|---|---|---|
| **Runtime** | *a program* | The engine that executes your compiled code. Also called the CLR — see [3.2](3.02-clr-and-compilation.md). |
| **SDK** | *a toolkit you install* | What you need to **build** code: compiler, `dotnet` CLI, build system. Includes a runtime. |
| **Class library** | *a set of built-in types* | The types you use every day — `List<T>`, `String`, `HttpClient`. |
| **.NET Framework** | *the original product (2002)* | Windows only. Installed **into** Windows, so one shared copy per machine. Ended at 4.8. |
| **.NET Core** | *the rewrite (2016)* | Cross-platform, open source, much faster. Ships **with your app**. Ended at 3.1. |
| **.NET 5+** | *the unified product (2020)* | .NET Core, renamed. The current one. Versions 5, 6, 7, 8, 9, 10. |
| **TFM** | *a short code in your `.csproj`* | Target Framework Moniker. Says which .NET you build against — `net10.0`, `net48`. |
| **Side-by-side** | *an installation model* | Several runtime versions installed at once, each app using its own. Impossible with Framework. |
| **Self-contained** | *a publish mode* | Your app ships **with** its runtime, so the target machine needs nothing installed. |
| **LTS / STS** | *support lengths* | Long-Term Support (3 years, even numbers) vs Standard-Term Support (18 months, odd). See [3.10](3.10-release-cadence.md). |
| **ASP.NET Core** | *the web framework* | Confusingly **kept** the word "Core" after the rename. ASP.NET Core 10 runs on .NET 10. |

## The concept

### First, what does ".NET" actually mean?

Before comparing versions it helps to know what the word covers. It is three things bundled
together:

1. **A runtime** — the program that runs your compiled code.
2. **A class library** — thousands of ready-made types.
3. **Tools** — the compiler, the `dotnet` command, the build system.

When someone asks "which .NET are you on?", they mean which version of that bundle.

### Why there are three generations

The story explains almost everything else, so it is worth knowing.

**2002 — .NET Framework.** Microsoft built .NET for Windows. It was tied deeply into Windows
and installed *into* the operating system rather than shipped with your app.

That worked for years. Then two problems grew.

**Problem one: it only ran on Windows.** The industry moved to Linux servers, containers and
cloud hosting. .NET could not follow.

**Problem two: only one version could exist per machine.** Because it lived inside Windows,
every application on that machine shared it. Upgrading it for one app risked breaking all the
others. Teams became afraid to upgrade, so servers sat on ancient versions for years.

**2016 — .NET Core.** Rather than patch the old one, Microsoft rewrote it from scratch. The
result was cross-platform, much faster, open source, and — crucially — **shipped with your
application** rather than installed into the OS.

The cost was that it started empty. Not everything from Framework came across.

**2020 — .NET 5.** By then Core had caught up. Having two products both called ".NET" was
confusing, so the names merged. .NET Core 3.1 was followed by **.NET 5**, and it has been a
single product ever since.

### ⚠️ The naming trap

There is no .NET Core 4 and no .NET 5 Framework. Microsoft **deliberately skipped 4**.

Why? Because .NET Framework 4.x already existed. A ".NET 4" would have been endlessly
confused with it. Jumping to 5 made it unmistakable.

| If you see | It means |
|---|---|
| .NET Framework 1.0 → 4.8 | The **old** Windows-only one |
| .NET Core 1.0 → 3.1 | The **rewrite**, before the rename |
| .NET 5, 6, 7, 8, 9, 10 | The **modern** one (Core, renamed) |

## How it works

### The simple version — what actually differs

| | .NET Framework | .NET (modern) |
|---|---|---|
| Runs on | Windows only | Windows, Linux, macOS |
| Where it lives | Installed into Windows | Ships with your app |
| Versions per machine | One, shared by everything | As many as you like |
| Open source | No | Yes |
| Still developed? | **No** — security fixes only | Yes, yearly releases |
| Speed | Slower | Much faster |
| Containers | Poor fit | Designed for it |

### How it actually works — the side-by-side point

This is the difference that mattered most in practice.

**With .NET Framework**, a server has one copy of .NET inside Windows. Every application uses
it. Upgrade it because App A needs a new feature, and Apps B and C are suddenly running on a
version nobody tested them against.

**With modern .NET**, each app either carries its own runtime or picks from several installed
side by side. App A on .NET 8 and App B on .NET 10 coexist on one machine and never interact.
You upgrade one without telling the other team.

This is also why .NET works properly in containers. A container image holds one app and its
exact runtime. Nothing is shared, so nothing conflicts.

### The deeper detail — what got left behind

The rewrite dropped some Windows-specific pieces **permanently**:

- **Web Forms** (`.aspx`) — replaced by Razor Pages and Blazor
- **WCF server-side** — replaced by gRPC ([21.6](../21-advanced-features/21.06-grpc.md)); the
  community CoreWCF project covers some client cases
- **.NET Remoting** — replaced by HTTP and gRPC
- **App domains** — partly replaced by `AssemblyLoadContext` ([3.6](3.06-assemblies-nuget.md))

If a legacy app depends on any of these, migrating means rewriting that part rather than
upgrading. That is the honest answer to "why is that old app still on Framework?" — usually
one of these four, or a third-party library that was never ported.

**WPF and WinForms did make the jump** and run on modern .NET. They are desktop UI
frameworks, so naturally they remain Windows-only.

## Code

The version a project targets is one line in the `.csproj`:

```xml
<!-- Modern .NET -->
<TargetFramework>net10.0</TargetFramework>

<!-- Old .NET Framework -->
<TargetFramework>net48</TargetFramework>
```

Checking what a machine has installed:

```bash
dotnet --version          # the SDK version currently in use
dotnet --list-runtimes    # every runtime installed side by side
dotnet --list-sdks        # every SDK installed
```

A typical `--list-runtimes` output shows the side-by-side idea directly:

```
Microsoft.AspNetCore.App 8.0.11
Microsoft.AspNetCore.App 10.0.0
Microsoft.NETCore.App 8.0.11
Microsoft.NETCore.App 10.0.0
```

Two versions, both present, neither interfering. That was impossible with .NET Framework.

## Interview questions

**Q: What is the difference between .NET Framework and .NET Core?**

.NET Framework is the original from 2002. It runs only on Windows and is installed into the
operating system, so every app on a machine shares one copy. .NET Core was a complete rewrite
released in 2016 — cross-platform, open source, considerably faster, and shipped with your
application rather than installed into the OS, which means different apps on one server can
safely use different versions. .NET Core was renamed to just .NET at version 5, so the modern
product is the continuation of Core, not of Framework.

**Q: Why did Microsoft skip .NET 4?**

Because .NET Framework 4.x already existed and had done for over a decade. Calling the new one
.NET 4 would have been constantly confused with .NET Framework 4.8, which is a completely
different product. Jumping from .NET Core 3.1 straight to .NET 5 made it unambiguous that this
was the unified successor rather than a Framework update.

**Q: Should a new project use .NET Framework?**

No. .NET Framework 4.8 is the final version — it receives security patches but no new features
and never will. Anything new should target the current .NET, preferably an LTS release. The
only reason to touch Framework today is maintaining an existing app that depends on something
never ported, such as Web Forms or server-side WCF.

**Q: What was dropped in the move to .NET Core?**

The pieces tied fundamentally to Windows or to old architecture: Web Forms, server-side WCF,
.NET Remoting, and app domains. They were replaced rather than ported — Razor Pages and Blazor
for Web Forms, gRPC for WCF and Remoting, `AssemblyLoadContext` for app domains. WPF and
WinForms did come across and run on modern .NET, though naturally still only on Windows. In
practice, when an app is stuck on Framework it is usually one of those four or a third-party
dependency that was never updated.

## Traps ⚠️

- **.NET 4.8 and .NET 8 are not related.** One is the final old version; the other is a modern
  release. The close numbers are historical accident.
- **"Core" was dropped from the runtime name but kept by ASP.NET Core.** ASP.NET Core 10 runs
  on .NET 10. This confuses everybody.
- **.NET Framework is not deprecated, it is finished.** Still supported and patched — but no
  new features, ever.
- **Not everything ported.** Web Forms, server-side WCF and Remoting are gone permanently.
- **Saying "dotnet core" today sounds dated.** The product has been called .NET since 2020.
