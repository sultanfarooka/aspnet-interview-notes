# 3.1 — .NET Framework vs .NET Core vs .NET 5+

## TL;DR

There have been **three generations of .NET**: Framework (2002, Windows only), Core (2016,
the cross-platform rewrite), and .NET 5+ (2020, where the names merged back into one).

- **.NET Framework 4.8 is the final version, forever.** Security fixes only. No new features.
- Today there is just **one .NET**. ".NET 8" or ".NET 10" always means the modern one.
- **.NET 4.8 and .NET 8 are unrelated products.** The similar numbers are an accident of history.

---

## Definitions

| Term | What it is | What it means |
|---|---|---|
| **Runtime** | *a program* | The engine that executes your compiled code. Also called the CLR — see [3.2](3.02-clr-and-compilation.md). |
| **SDK** | *a toolkit* | What you install to **build** code: compiler, `dotnet` CLI, build system. Includes a runtime. |
| **Class library** | *a set of types* | The built-in types you use every day — `List<T>`, `String`, `HttpClient`. |
| **.NET Framework** | *the original product (2002)* | Windows only. Installed **into** Windows, so one shared copy per machine. Ended at 4.8. |
| **.NET Core** | *the rewrite (2016)* | Cross-platform, open source, much faster. Ships **with your app**. Ended at 3.1. |
| **.NET 5+** | *the unified product (2020)* | .NET Core, renamed. The current one. Versions 5, 6, 7, 8, 9, 10. |
| **TFM** | *a short code in your `.csproj`* | Target Framework Moniker. Says which .NET you build against — `net10.0`, `net48`. |
| **Side-by-side** | *an installation model* | Several runtime versions installed at once, each app using its own. Impossible with Framework. |
| **Self-contained** | *a publish mode* | Your app ships **with** its runtime, so the target machine needs nothing installed. |
| **LTS / STS** | *support lengths* | Long-Term Support (3 years, even numbers) vs Standard-Term Support (18 months, odd numbers). See [3.10](3.10-release-cadence.md). |
| **ASP.NET Core** | *the web framework* | Confusingly **kept** the word "Core" after the rename. ASP.NET Core 10 runs on .NET 10. |

## The concept

### First, what is ".NET"?

Before comparing versions, it helps to be clear what the word means. It is three things
bundled together:

1. **A runtime.** The program that actually runs your compiled code.
2. **A class library.** Thousands of ready-made types like `List<T>`, `String` and `HttpClient`.
3. **Tools.** The compiler, the `dotnet` command, the build system.

When people say "which .NET are you on?", they are asking which version of that bundle you
are using.

### Why there are three versions

Here is the story, and it explains almost everything else.

**2002 — .NET Framework.** Microsoft built .NET for Windows. It was deeply tied into
Windows, and it was installed *into* Windows rather than shipped with your app. That worked
well for years.

Then two problems grew:

- **It only ran on Windows.** The industry moved to Linux servers, containers and cloud
  hosting. .NET could not go there.
- **Only one version could exist per machine.** Because it was installed into Windows,
  every application on that machine shared it. Upgrading it for one app risked breaking
  every other app. This was a real and constant problem.

**2016 — .NET Core.** Rather than patch the old one, Microsoft rewrote it from scratch. The
new one was cross-platform, much faster, open source, and — importantly — **shipped with
your application** instead of being installed into the operating system. Ten apps on one
server could each use a different version and never interfere.

The cost was that it was a fresh start, so it did not have everything the old one had.

**2020 — .NET 5.** By this point .NET Core had caught up. Having two products called ".NET"
was confusing, so Microsoft merged the names. .NET Core 3.1 was followed by **.NET 5**, and
it has been one product ever since.

### The naming trap ⚠️

There is no .NET Core 4, and no .NET Framework 5. Microsoft **skipped version 4** on purpose.

Why? Because .NET Framework 4.x already existed. A ".NET Core 4" or ".NET 4" would have been
constantly mistaken for it. Jumping to 5 removed the ambiguity.

So the number tells you which family you are in:

| If you see | It means |
|---|---|
| .NET Framework 1.0 → 4.8 | The **old** Windows-only one |
| .NET Core 1.0 → 3.1 | The **rewrite**, before the rename |
| .NET 5, 6, 7, 8, 9, 10 | The **modern** one (Core, renamed) |

**.NET 4.8 and .NET 8 are wildly different things**, despite the similar-looking numbers.
That confusion is exactly why the version was skipped.

## How it works

### The simple version — what actually differs

| | .NET Framework | .NET (modern) |
|---|---|---|
| Runs on | Windows only | Windows, Linux, macOS |
| Where it lives | Installed into Windows | Ships with your app |
| Versions per machine | One, shared by everything | As many as you like |
| Open source | No | Yes |
| Still developed? | **No** — security fixes only | Yes, yearly releases |
| Speed | Slower | Much faster |
| Containers | Poor fit | Designed for it |

### How it actually works — the side-by-side installation point

This is the difference that mattered most in practice, so it is worth being concrete.

**With .NET Framework**, your server has one copy of .NET installed in Windows. Every
application on that box uses it. If you upgrade it because App A needs a new feature, App B
and App C are now running on a version they were never tested against. Teams became terrified
of upgrading, so machines sat on old versions for years.

**With modern .NET**, the runtime is either published alongside your app or installed as one
of several versions side by side. App A can be on .NET 8 and App B on .NET 10, on the same
machine, with no interaction at all. You can upgrade one without even telling the other team.

This is also why .NET works properly in containers. A container image holds one app and its
exact runtime. Nothing is shared, so nothing conflicts.

### The deeper detail — what got left behind

The rewrite dropped some Windows-specific things permanently. They will never come back:

- **Web Forms** (`.aspx` pages) — replaced by Blazor and Razor Pages
- **WCF server-side** — replaced by gRPC ([21.6](../21-advanced-features/21.06-grpc.md)); a
  community project called CoreWCF exists for clients
- **.NET Remoting** — replaced by HTTP and gRPC
- **App domains** — partially replaced by `AssemblyLoadContext`
  ([3.6](3.06-assemblies-nuget.md))

If a legacy application depends on any of these, migrating is a rewrite of that part rather
than an upgrade. That is the honest answer to "why is that old app still on Framework?" —
usually one of these four, or a third-party library that was never ported.

WPF and WinForms **were** brought forward and work on modern .NET, but only on Windows —
they are desktop UI frameworks, so that is expected.

## Code

You can see which .NET a project targets by looking at one line in the `.csproj` file:

```xml
<!-- Modern .NET -->
<TargetFramework>net10.0</TargetFramework>

<!-- Old .NET Framework -->
<TargetFramework>net48</TargetFramework>
```

That value is called a **TFM**, short for Target Framework Moniker. It is just a short code
saying which .NET you are building against. More in [3.7](3.07-csproj-and-tfm.md).

Checking what is installed on a machine:

```bash
dotnet --version          # the SDK version being used
dotnet --list-runtimes    # every runtime installed side by side
dotnet --list-sdks        # every SDK installed
```

A typical `--list-runtimes` output shows the side-by-side idea clearly:

```
Microsoft.AspNetCore.App 8.0.11
Microsoft.AspNetCore.App 10.0.0
Microsoft.NETCore.App 8.0.11
Microsoft.NETCore.App 10.0.0
```

Two versions, both present, neither interfering with the other. That was impossible with
.NET Framework.

## Interview questions

**Q: What is the difference between .NET Framework and .NET Core?**

.NET Framework is the original, from 2002. It only runs on Windows and it is installed into
the operating system, so every application on a machine shares one copy. .NET Core was a
complete rewrite released in 2016. It runs on Windows, Linux and macOS, it is open source,
it is considerably faster, and it ships with your application rather than being installed
into the OS — which means different apps on the same server can use different versions
safely. .NET Core was renamed to just .NET at version 5, so the modern product is the
continuation of Core, not of Framework.

**Q: Why did Microsoft skip .NET 4?**

Because .NET Framework 4.x already existed and had done for years. Calling the new one .NET 4
would have been endlessly confused with .NET Framework 4.8, which is a completely different
product. Jumping straight from .NET Core 3.1 to .NET 5 made it unambiguous that this was the
unified successor rather than a Framework update.

**Q: Should a new project use .NET Framework?**

No. .NET Framework 4.8 is the final version — it receives security patches but no new
features, and it never will. Anything new should target the current .NET, and preferably an
LTS release. The only reason to touch Framework now is maintaining an existing application
that depends on something never ported, such as Web Forms or server-side WCF.

**Q: What was dropped in the move to .NET Core?**

The pieces that were fundamentally tied to Windows or to old architecture: Web Forms,
server-side WCF, .NET Remoting, and app domains. Those were replaced rather than ported —
Blazor and Razor Pages for Web Forms, gRPC for WCF and Remoting, `AssemblyLoadContext` for
app domains. WPF and WinForms did make the jump and run on modern .NET, but naturally only
on Windows. In practice, when a legacy app is stuck on Framework, it is usually one of those
four or a third-party dependency that was never updated.

## Traps ⚠️

- **.NET 4.8 and .NET 8 are not related.** One is the final old version, the other is a
  modern release. The numbers being close is an accident of history.
- **"Core" is no longer used in the name** for the runtime — but **ASP.NET Core kept it**.
  ASP.NET Core 8 runs on .NET 8. That naming survived for brand reasons and confuses
  everyone.
- **.NET Framework is not "deprecated", it is finished.** It is still supported and still
  patched, which is different from being abandoned. But no new features will ever ship.
- **Not everything ported.** Web Forms, server-side WCF and Remoting are gone permanently.
- **.NET Standard is a separate thing again** and mostly historical now. See
  [3.9](3.09-dotnet-standard.md).
- **Saying "dotnet core" in an interview today sounds dated.** The product has been called
  .NET since 2020.
