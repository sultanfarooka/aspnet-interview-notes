## TL;DR

- In C#, polymorphism is a variable declared as a **base type** holding a **derived type** object — and calling a method on it runs the *derived* version.
- **Runtime** polymorphism = `virtual` + `override`. C# decides at runtime from the actual object.
- **Compile-time** polymorphism = method overloading. The compiler decides from the arguments you passed.

---

## The concept

In C#, polymorphism is what happens when **a variable declared as one type holds an object
of a derived type — and calling a method on that variable runs the derived type's version,
not the declared type's.**

That sentence is the whole topic. Here it is as C# code:

```csharp
public class Animal
{
    public virtual string Speak() => "...";
}

public class Dog : Animal
{
    public override string Speak() => "Woof";
}
```

```csharp
Animal a = new Dog();   // declared type: Animal.   actual object: Dog.

a.Speak();              // "Woof" — Dog's version runs, not Animal's
```

Look at that first line. **Two different types are in play**, and each one controls
something different:

| | What it controls |
|---|---|
| **Declared type** — `Animal`, on the left of `=` | **What you are allowed to call.** The compiler only lets you call members that exist on `Animal`. Write `a.Fetch()` and it will not compile, even though the object really is a `Dog`. |
| **Actual object** — `Dog`, on the right of `=` | **Which implementation runs.** At runtime, C# looks at the real object and runs its `override`. |

So the **compiler checks against `Animal`**, and the **runtime dispatches to `Dog`**. That
split is the mechanism, and it is what "polymorphism" names in C#.

### Why C# bothers

Because it lets you type a parameter as the base class and accept every subclass — including
ones that do not exist yet:

```csharp
void Describe(Animal animal)          // accepts Dog, Cat, Horse, anything : Animal
    => Console.WriteLine(animal.Speak());

Describe(new Dog());                  // "Woof"
Describe(new Cat());                  // "Meow"
```

`Describe` was compiled without knowing `Cat` existed. It still calls the right method.

### The three ways to get it in C#

```csharp
// 1. virtual on a base class — there IS a default, subclasses may replace it
public class Animal { public virtual string Speak() => "..."; }

// 2. abstract on a base class — there is NO default, subclasses MUST supply one
public abstract class Shape { public abstract double Area(); }

// 3. an interface — no base class involved at all
public interface IPaymentMethod { Task PayAsync(decimal amount); }
```

All three give you the same runtime behaviour: a base-typed (or interface-typed) reference
running the concrete type's implementation.

### The two categories interviewers ask for

| | C# keyword | Decided | By what |
|---|---|---|---|
| **Compile-time** (static) | method overloading | before the program runs | the *arguments* at the call site |
| **Runtime** (dynamic) | `virtual` / `override` | while the program runs | the *actual object* |

Runtime polymorphism is the one that matters. Compile-time polymorphism is really just a
convenience for naming.

## How it works

### Compile-time polymorphism (overloading)

Several methods share a name but take different parameters. The compiler works out which
one you meant by looking at the arguments at the call site.

```csharp
public class Calculator
{
    public int Add(int a, int b) => a + b;
    public double Add(double a, double b) => a + b;
    public int Add(int a, int b, int c) => a + b + c;
}

calc.Add(1, 2);        // picks the first — two ints
calc.Add(1.5, 2.5);    // picks the second — two doubles
calc.Add(1, 2, 3);     // picks the third — three ints
```

This is decided **before the program ever runs**. By the time the code executes, the
decision is already baked in. That is why it is called compile-time (or "static")
polymorphism.

What counts as a different overload: the number of parameters, their types, or their order.

**What does NOT count: the return type.** This is a common exam-style question:

```csharp
public int GetValue() => 1;
public string GetValue() => "1";
// ERROR. You cannot overload on return type alone.
```

The reason is simple — if you write `GetValue();` on its own line and ignore the result,
the compiler would have no way to know which one you meant.

Operator overloading is also compile-time polymorphism. See
[1.19](1.19-indexers-operators.md).

### Runtime polymorphism (overriding)

The mechanism from the concept section, on a more realistic example. Here `Shape` uses
`abstract` rather than `virtual`, because there is no sensible default area to inherit —
every shape must supply its own.

```csharp
public abstract class Shape
{
    public abstract double Area();
}

public class Circle(double radius) : Shape
{
    public override double Area() => Math.PI * radius * radius;
}

public class Rectangle(double w, double h) : Shape
{
    public override double Area() => w * h;
}
```

Now the payoff:

```csharp
List<Shape> shapes =
[
    new Circle(1),
    new Rectangle(2, 3),
    new Circle(5)
];

double total = shapes.Sum(s => s.Area());
// Each s.Area() call runs the RIGHT version automatically.
// This loop has no idea circles or rectangles exist.
```

Look at that last line closely. The code says `s.Area()` where `s` is just a `Shape`. It
does not check the type. It does not have an `if` or a `switch`. Yet each object runs its
own correct calculation.

**And this is the real benefit:** if you add a `Triangle` class tomorrow, this loop keeps
working with no changes at all. That is polymorphism paying for itself.

Compare with what you would otherwise write:

```csharp
// The version WITHOUT polymorphism — every new shape means editing this
double total = 0;
foreach (var s in shapes)
{
    if (s is Circle c) total += Math.PI * c.Radius * c.Radius;
    else if (s is Rectangle r) total += r.Width * r.Height;
    // ...and you must remember to come back here for every new shape
}
```

A long chain of type checks like this is a strong hint that polymorphism is the better
answer. This is also what the open/closed principle in SOLID is about — see
[22.1](../22-architecture-patterns/22.01-solid.md).

### Interfaces give you polymorphism too

You do not need inheritance. An interface works just as well:

```csharp
public interface IPaymentMethod { Task PayAsync(decimal amount); }

public class CreditCard : IPaymentMethod { /* ... */ }
public class PayPal     : IPaymentMethod { /* ... */ }

// Works with any payment method, present or future
async Task Checkout(IPaymentMethod method, decimal amount)
    => await method.PayAsync(amount);
```

This is usually the preferred approach in modern C#, because it does not force your types
into an inheritance hierarchy.

## Code

Putting both kinds together:

```csharp
public abstract class Notifier
{
    // Runtime polymorphism — each subclass sends differently
    public abstract Task SendAsync(string recipient, string message);

    // Compile-time polymorphism — three convenient ways to call it
    public Task SendAsync(User user, string message)
        => SendAsync(user.Email, message);

    public Task SendAsync(IEnumerable<User> users, string message)
        => Task.WhenAll(users.Select(u => SendAsync(u, message)));
}

public class EmailNotifier(IEmailSender sender) : Notifier
{
    public override Task SendAsync(string recipient, string message)
        => sender.SendAsync(recipient, "Notification", message);
}

public class SmsNotifier(ISmsGateway gateway) : Notifier
{
    public override Task SendAsync(string recipient, string message)
        => gateway.SendTextAsync(recipient, message);
}
```

Now calling code just holds a `Notifier` and calls `SendAsync`. It does not know or care
whether an email or a text message goes out.

## Interview questions

**Q: What is polymorphism?**

It means one name can behave in different ways depending on the context. C# has two forms.
Compile-time polymorphism is method overloading — several methods share a name but take
different parameters, and the compiler picks the right one from the arguments. Runtime
polymorphism is method overriding — a base class declares a virtual method, derived classes
override it, and the runtime picks the version matching the actual object. The second one
is the important one, because it lets you write code that works with types that did not
exist when you wrote it.

**Q: What is the difference between overloading and overriding?**

Overloading is several methods with the same name in the same class, differing by their
parameters, resolved by the compiler before the program runs. Overriding is a derived class
replacing a virtual method from its base class, resolved by the runtime based on the actual
object. So overloading is about convenience at the call site, and overriding is about
substituting behaviour.

**Q: Can you overload a method by changing only the return type?**

No. If you called the method and ignored its result, the compiler would have no information
to decide which one you meant. Overloads have to differ by the number, types, or order of
their parameters.

**Q: How does polymorphism help in real code?**

It lets you write code that works with future types. If I have a list of shapes and call
`Area()` on each one, I never have to touch that loop again when someone adds a new shape.
Without it, you end up with a growing chain of type checks that has to be updated in every
place whenever a new type appears — and eventually someone forgets one. That is exactly
what the open/closed principle is warning about.

## Traps ⚠️

- **`new` does not give you polymorphism.** It hides the base method, and which version
  runs depends on the variable's declared type, not the object. See
  [1.7](1.07-inheritance.md).
- **A method must be `virtual` or `abstract` to be overridden.** Marking it `override` in
  the derived class is not enough on its own.
- **Overload resolution can surprise you.** When you pass a `null`, or a type that could
  convert to several parameter types, the compiler picks by rules that are not always
  obvious. Cast explicitly when it is ambiguous.
- **Long `if (x is TypeA) ... else if (x is TypeB)` chains** usually mean polymorphism was
  the better design.
- **Polymorphism is not free at runtime.** A virtual call costs a lookup. It is almost
  never worth worrying about, but it is why `sealed` can help in genuinely hot code.
